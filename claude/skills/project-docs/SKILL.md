# Project docs

Docs are read by people who don't have the code open: users, self-hosters, contributors, future maintainers. A wrong doc costs more than a missing one, because the reader trusts it. The job is few pages, each true, each with one purpose.

## The test

For every section: does the reader need it, and will it stay true without someone remembering to update it?

- Needed and stable → write it.
- Needed, but restates a config file, the code or `--help` → link to the source (the Justfile recipe, `.env.example`, `package.json` scripts). A short copy is allowed only on a page the reader follows step by step, with the source named next to it.
- Not needed → leave it out.

Goes in:

- What the project is and why, in one or two sentences.
- How to install, run, configure, deploy, verify: steps that work when pasted.
- Reference the reader looks up (CLI flags, config keys, API routes) when nothing generates it.
- The why behind what a user or contributor will question: limits, trade-offs, privacy rules.
- Troubleshooting for failures that actually happened.

Stays out:

- Work tracking: TODO lists, plans, audits, roadmaps, status logs, "next steps". See below.
- Dated wording: "currently", "new", "soon", "for now", "as of", future features. Only the CHANGELOG is dated.
- Directory maps, architecture tours, code walkthroughs: the code is the source of truth. An explanation page giving the why is fine.
- Version lists, env var tables, command tables copied from config.
- Agent instructions: they go in CLAUDE.md (`claude-md` skill). Never send a human reader to CLAUDE.md.
- Scaffold boilerplate left by a template.
- Secrets, hosts, IPs, personal paths (`/home/<user>/…`).

## Work tracking lives outside the repo

- Ideas → `~/notes/<project>.md` (`note-idea` skill).
- Multi-phase plans → `~/.claude/plans/` (`plan-phase` skill).
- Tickets and roadmaps → Notion, kan.bn or GitHub Issues. The README links only a tracker the public can open; with none, it points to GitHub Issues.
- Architecture decisions → ADRs in `docs/adr/` (`domain-modeling` skill).
- A TODO, PLAN, AUDIT or NOTES file found in a repo: list what is live, done or stale, propose where the live items go, and delete the file only once the user agrees. Git history is the archive; no `docs/archive/`.

## One type per page

- **How-to**: steps to reach one goal (install, deploy, restore, release). The title names the task.
- **Reference**: neutral, complete description of flags, keys, routes, mirroring the code. No instructions.
- **Explanation**: the why, trade-offs, design choices.
- **Tutorial**: one guided path for a newcomer. Rare in these projects; most need how-to and reference.

A page that mixes types is split, and the parts link to each other. Never create empty sections for types the project doesn't need.

## README

The root README is the entry point, in this order:

1. Title and one-line pitch, the same as the repo and `package.json` description.
2. Status, when not production-ready.
3. Install and run: the shortest path that works when pasted.
4. Develop and verify: point to the check recipe instead of listing its steps.
5. Links: `docs/` pages, every package README in a monorepo, the tracker.
6. License.

Past about 100 lines, sections move to `docs/`, one link deep from the README. A package README covers its package and links back to the root.

## Language

- English for every doc, unless the product's whole audience speaks one other language (a French-only site): then that language only, with no English copy. Any other doc in another language is migrated to English when touched by an audit.
- Another language only when the product itself supports it, or when the user asks for a translation. Translations live in `docs/<lang>/`, with the same tree and file names as the English pages. The README translation is `docs/<lang>/README.md` (or `docs/<lang>/index.md` on a docs site), linked from the top of the English README.
- A translation changes in the same commit as its English source. When a change can't be translated faithfully, report the page as behind instead of leaving it silently stale.

## CHANGELOG

- Generated by the release tool (release-it with conventional-changelog): never edit it by hand. Noise such as empty versions is fixed in the release config.
- Hand-written (Keep a Changelog): add the user-visible change under `## [Unreleased]` in the same commit, in the reader's terms, not the commit's.

## Style

- Problem before solution. Headings name the task ("Deploy with Docker", not "Docker").
- One term per concept, the one the code and UI use.
- No "simply", "just", "easily", "obviously".
- Commands in fenced blocks without a `$` prompt, placeholders as `<name>`.

## Editing mid-task

1. A change renames or alters a command, flag, env var, config key, route or behavior → grep the docs (`README*`, `docs/`, package READMEs) for the old name and fix every hit in the same change.
2. Find the page that already covers the subject and update it instead of adding one. Check the content fits that page's type.
3. Apply the test. If it fails, add nothing and say so in one line.
4. Run each command you wrote or changed when it is safe locally (build, check, `--help`); otherwise check that the recipe or script exists. Check every path and link you touched.
5. Update the translations of each page you changed, or name the ones now behind.
6. Delete any sentence the change made untrue.

Done when no doc names the old behavior and every command, path and link you touched was checked.

## Full audit

When asked to audit a repo's docs, or when creating them:

1. Inventory every human-facing `.md` outside `node_modules`: lines, type, audience, language.
2. Check every command, path, script, env var, port and version against the Justfile, `package.json`, compose files, `.env.example` and the code. Check relative links and anchors (`lychee --offline .` when installed).
3. Classify every section: keep, cut (restates config or code), move (other page, other type, out of the repo), stale, to translate.
4. Check the README has the entry-point sections and links to every package and doc page.
5. Rewrite one page at a time.
6. Report per file: size before and after, what moved where, what was cut, and what needs the user (tracker items to move, translations, files to delete).

Done when every section was classified and every command, path and link was checked.
